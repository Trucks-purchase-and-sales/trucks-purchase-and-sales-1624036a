=====================================================================
Bug 1: opportunity_status_history has no writer in the reconstructed
schema
=====================================================================
Failing assertion: "status history inherits parent visibility" expected
>0 rows after the seller's own opportunity transitioned brouillon ->
envoyee; got 0. Not an RLS bug -- the SELECT policy on this table was
already correctly reconstructed (staging-schema.sql section 8, from
the real Phase 2 audit). Nothing had ever WRITTEN a row: the trigger
that populates this table on status change is one of the ~13 business-
logic-only triggers ADR-005 already named as deliberately excluded
("status-history logging"), confirmed by migration
20260819005000_workflow_children_parent_scope.sql's own comment
("generated by trusted triggers") -- the trigger body itself was never
tracked in git, only the RLS policy referencing the table.

Fix: added staging-schema.sql section 13, a reasonable-effort
RECONSTRUCTION (not a recovered original -- that's not possible) of a
minimal status-history-logging trigger: fires on any
vehicle_opportunities.status change, inserts old_status/new_status/
changed_by_user_id (auth.uid()). Matches the table's own column shape
exactly. Explicitly documented in the file as a reconstruction, same
honesty standard as section 11's rate_limit_check.

Checked for regression risk before adding: this trigger only fires on
UPDATE, not INSERT, so seeding an opportunity directly at any status
(the pattern almost every Playwright E2E test in this repo uses) does
NOT create a history row. Grepped e2e/tests/ for any direct
.update(...status...) on vehicle_opportunities and found none -- the
only place that genuinely transitions vehicle_opportunities.status via
an UPDATE is inside the tests/staging/*.staging.ts suites themselves
(security.staging.ts, workflow-children.staging.ts,
workflow-transactions.staging.ts, photo-handoff.staging.ts), all
already being fixed in this same pass. Residual risk: if a FUTURE
Playwright test starts calling a UI action that updates
vehicle_opportunities.status and then deletes the opportunity in
cleanup, it will need the same fix applied below -- easy and
well-understood if it happens, not fixed pre-emptively for tests that
don't exist yet.

=====================================================================
Bug 2: cleanup order -- children before parent
=====================================================================
Second failure was the test's own afterAll: deleting
vehicle_opportunities directly, without first deleting the
information_requests row the test itself inserted, hit
"foreign key constraint info_req_vehicle_opportunity_id_fkey" (none of
the FKs in this hand-reconstructed schema cascade on delete -- confirmed
by grepping every vehicle_opportunity_id FK definition in
staging-schema.sql, all plain `references`, no ON DELETE CASCADE
anywhere). This is a genuine test-code bug, not a schema issue: the
exact same "delete children before the parent" pattern this whole V2P
session's own Playwright tests have needed repeatedly all along.

Proactively checked the other three staging suites for the same
pattern rather than waiting for each to fail in turn (they were all
about to run next in the same CI job):
  - security.staging.ts: transitions status multiple times but never
    inserts into information_requests/opportunity_activities/
    vehicle_photos directly -- only needed the new
    opportunity_status_history cleanup (which didn't exist as a
    problem until Bug 1's fix made this table start getting rows).
  - workflow-children.staging.ts: needed opportunity_activities,
    information_requests, and opportunity_status_history cleared first.
  - workflow-transactions.staging.ts: needed vehicle_photos,
    information_requests (populated indirectly via the
    admin_handover_to_partner/admin_request_information RPCs), and
    opportunity_status_history cleared first.
  - photo-handoff.staging.ts: needed vehicle_photos and
    opportunity_status_history cleared first.
All four fixed with the identical pattern: explicit child-table
deletes filtered by the tracked opportunity IDs, immediately before
the existing vehicle_opportunities delete, inside the same afterAll.
