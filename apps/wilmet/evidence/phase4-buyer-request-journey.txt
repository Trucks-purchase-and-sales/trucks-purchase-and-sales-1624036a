V2P Phase 4 -- buyer request journey (anonymous submission)
Written by: Claude, 2026-08-25.

Adds e2e/tests/buyer-request-journey.pw.ts, extending the existing
public-smoke.pw.ts coverage (which only reached the wizard's first
step) all the way through a real submission -- the buyer side's "money
critical path", matching the plan's example critical smoke journeys.

Scope: an anonymous visitor (no login -- buyer_leads allows a public
anon INSERT by design, confirmed in inventory.md's live RLS audit)
fills the minimum required fields across all 4 wizard steps and
submits. Read buyerLeadSchema (src/lib/buyer-leads.schema.ts)
directly rather than guessing: only vehicle_category, vehicle_type
(step 1) and first_name, last_name, email, gdpr_consent (step 4) are
actually required: everything on steps 2 and 3 is optional, so the
test advances through them without filling anything. Confirmed
per-step validation only checks that step's own fields
(chercher-un-vehicule.index.tsx's `next()` calls
`form.trigger(stepFields[step])`), so this minimal-fill approach is
exactly what the app itself allows, not a workaround.

Vehicle category/type are the SearchableCombobox component (search-as-
you-type popover, components/pickers/SearchableCombobox.tsx), not a
plain <select> -- added selectFirstComboboxOption() to a new shared
e2e/tests/helpers/form.ts (also holds labeledInput(), extracted from
opportunity-crud-journey.pw.ts's own Field/Label workaround, now
reused here). The test picks whichever option is listed first since
it isn't asserting on a specific vehicle type.

Confirmed a fourth instance of the same missing htmlFor/id association
already flagged in phase4-e2e-smoke-suite.txt Finding #2 (auth form)
and phase4-opportunity-edit-and-delete-gap.txt (opportunity wizard) --
this form's own Field component (chercher-un-vehicule.index.tsx, a
separate implementation from the wizard's) has the identical gap. Four
independent implementations sharing the same bug strongly suggests
this is a systemic convention issue across the app's forms, not an
isolated mistake -- worth raising as one Lovable prompt covering the
pattern generally rather than four separate one-off fixes, whenever
that queued prompt is written.

Submission itself needs no service-role key (anonymous insert), but
cleanup does -- an anonymous submitter has no session to look up or
delete their own row afterward, and buyer_leads has no self-service
delete path anyway. The test captures the created row's id directly
from the POST /api/public/buyer-leads response body (via
page.waitForResponse()) and deletes it by id in afterEach, so it still
skips cleanly without E2E_SUPABASE_SERVICE_ROLE_KEY rather than
leaving rows behind in the disposable project when that secret is
present.

Not yet run locally (per Salma's instruction to verify through GitHub
Actions instead of this machine) -- lint-clean and discovery-validated
only; first real execution happens in this PR's CI run.

Update (2026-08-25) -- real finding, not a test bug: the first two CI
runs got past every selector issue and still hung, because
ref_vehicle_categories and ref_vehicle_types were completely empty in
the disposable staging project. Confirmed directly with a read-only
REST query (both returned `[]`). This blocks more than the test: the
SearchableCombobox never passes `allowCustom` for these two fields, so
there's no free-text fallback either -- with an empty category/type
list, the buyer request wizard is genuinely unusable end-to-end on
this project, for a real visitor exactly as much as for this test.

Root cause: apps/wilmet/staging-schema.sql's own closing comment
already said "seed a little synthetic reference data (ref_* tables)"
as a TODO from Phase 2 (ADR-005) -- it was never actually done. Every
earlier test that touched vehicle_opportunities sidestepped this by
saving drafts with every field left blank, so nothing before this ever
actually opened one of these comboboxes and needed real rows behind
it.

Fixed: seeded two rows each into ref_vehicle_categories
(camion/utilitaire) and ref_vehicle_types (porteur/tracteur) directly
in the live disposable project, and added the same two INSERT
statements (with `on conflict (slug) do nothing`) to
staging-schema.sql's new section 10, so a from-scratch rebuild of the
staging project reproduces this instead of silently missing it again.
Deliberately minimal -- just enough for the two fields this test
actually needs, not all 11 ref_* tables; extend later if a future test
needs brand/model or the other reference lists.

Update (2026-08-25) -- second real finding, this time a genuine bug in
the test itself, not the app: after the reference-data fix, submission
still hung with zero console/network activity captured by diagnostic
listeners. Root cause found by additionally capturing the sonner toast
region's text directly: "Merci de compléter les champs requis. Champ :
Nom" -- the app's own client-side validation (react-hook-form's
invalid-submit branch) was correctly rejecting the form, silently
jumping back to the offending step with only a toast, no console
message or network request at all (which is exactly why the earlier
listeners caught nothing -- there was nothing to catch).

The actual cause: labeledInput(page, "Nom") used Playwright's default
case-insensitive SUBSTRING match, which also matches "Prénom" (it
contains "nom"). Being first in the form, the Prénom field absorbed
the "Nom" fill too -- overwriting "E2E" with "Playwright" -- while the
real Nom field was left genuinely empty. Fixed by widening
labeledInput()/selectFirstComboboxOption() in helpers/form.ts to
accept a RegExp, and passing /^Nom/i (anchored, not a bare substring)
for this one ambiguous label. Every other label used across both
opportunity-crud-journey.pw.ts and this file was checked and has no
equivalent collision.

This is a good example of why the diagnostic-first approach (adding
console/network/toast capture instead of guessing another fix blind)
mattered: three earlier attempts across other tests this session fixed
real environment/selector issues by reasoning from error messages
alone, but this one produced no error at all -- only a silent,
correct rejection -- and would have taken many more blind guesses to
find without seeing the toast text directly.
