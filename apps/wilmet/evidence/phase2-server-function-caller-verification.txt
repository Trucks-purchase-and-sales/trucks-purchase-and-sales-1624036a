V2P Phase 2, section 9.3 -- server-function caller verification and
input validation (D7)
Written by: Claude, 2026-08-26.

Never previously audited by either this V2P pass or the earlier
ChatGPT-assisted pass (confirmed by grep: the string "Edge Function"
appears nowhere in the removed docs/security/ tree either -- see
ADR-009). Genuinely the last unverified item from the plan's Definition
of Done table. Wilmet's actual architecture is TanStack Start server
functions (`createServerFn`), not classic Supabase Edge Functions, so
D7's letter ("Edge Functions validate input server-side and verify the
caller") is re-mapped onto the equivalent real surface: every
`src/lib/*.functions.ts` module.

=====================================================================
Caller verification
=====================================================================
19 files define server functions (`createServerFn`). 17 of them import
and apply `requireSupabaseAuth` as middleware
(src/integrations/supabase/auth-middleware.ts, auto-generated by the
TanStack Start + Supabase integration -- not hand-written, so not
subject to the usual "did the vibe-coded version actually check
this" doubt).

Read the middleware directly rather than trusting its name. It:
  1. requires a real `Authorization: Bearer <token>` header on the
     request (not a client-supplied claim of identity);
  2. rejects anything that isn't a well-formed 3-part JWT;
  3. calls `supabase.auth.getClaims(token)` -- an actual signature/
     validity check against Supabase Auth, not a decode-and-trust;
  4. rejects if no `sub` (user id) claim resolves;
  5. passes a Supabase client scoped to THAT verified user's own JWT
     (respecting RLS as them) into the handler's context, plus the
     verified `userId` and `claims`.

Role-gated actions build correctly on top of this, not around it --
e.g. admin.functions.ts's `assertAdmin(sb, userId)` queries
`user_roles` filtered by the verified `userId` from the middleware,
never a client-supplied id. Same pattern confirmed in
dashboards.functions.ts's `hasAnyRoleServer`.

The 2 files that do NOT use requireSupabaseAuth are both deliberately
public, not oversights:
  - reference-data.functions.ts: public vehicle taxonomy lookups,
    RLS `true` on those tables (already independently verified in
    apps/wilmet/threat-model.md and phase2-rls-audit.txt).
  - public-catalog.functions.ts: published sale-listing catalogue for
    anonymous browsing, with its own explicit safe-column projection
    (own code comment: "internal fields... never leave the server") --
    the right defense-in-depth pattern for a public read endpoint, not
    a missing check.

No file was found using a service-role/admin Supabase client directly
without going through requireSupabaseAuth first. Narrow service-role
usage exists (e.g. `checkRateLimit()`, already documented in Phase 4's
evidence as needing SUPABASE_SERVICE_ROLE_KEY) but only inside helper
modules called FROM an already-authenticated createServerFn handler,
never as its own unguarded entry point -- confirmed by reading
buyer-leads.functions.ts's call into app-settings.server.ts and
affiliate.server.ts, both reached only after requireSupabaseAuth (or,
for the anonymous submission path, after the public route's own
rate-limit gate).

=====================================================================
Input validation
=====================================================================
16 of 19 files validate input with zod directly. The 3 that don't are
not gaps:
  - reference-data.functions.ts: GET, no meaningful input.
  - dashboards.functions.ts: GET, no meaningful input (confirmed by
    reading salesAgentKpis -- no body, only the verified userId from
    context is used).
  - buyer-leads.functions.ts: appeared zod-less on a direct grep
    because it validates through a named wrapper,
    `parseBuyerLead(data)` (src/lib/buyer-leads.schema.ts). Read the
    wrapper: it calls `buyerLeadSchema.safeParse(payload)` -- the
    SAME zod schema the client form uses via `zodResolver`, re-run
    server-side before any database write. Confirmed the anonymous
    submission path (src/routes/api/public/buyer-leads.ts) calls the
    identical `parseBuyerLead` wrapper too -- both the authenticated
    and anonymous submission paths get real server-side validation,
    not just client-side UX validation.

=====================================================================
CONCLUSION
=====================================================================
D7 is met, not open. Caller verification is real (framework-generated
JWT validation against Supabase Auth, not a stub), consistently
applied, with the 2 exceptions both deliberately and correctly public.
Input validation is real (zod, including on both buyer-lead submission
paths via a shared wrapper), with the 3 exceptions all being genuinely
input-less GET operations. This closes the last unverified item in the
plan's Definition of Done table (D7) -- previously assumed unaudited
by this V2P pass (see the "what's left across all phases" review,
2026-08-26) and confirmed absent from the earlier ChatGPT-era docs too.

Not found: any instance of a service-role bypass reachable without
prior caller verification. This is a genuinely clean result, not a
partial one -- no findings-register row was added for this item since
there is no defect to track, matching the same pattern already used
for Phase 2's RLS audit ("zero Critical/High findings" recorded in
evidence, not manufactured into a register row).
